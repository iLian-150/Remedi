# Remedi 前端设计与实现规范

本规范适用于学生端和教师端全部新页面、组件及交互。它是前端实现的硬性要求；与单页临时设计偏好冲突时，先遵守本规范并保持全站一致。

## 组件与依赖

1. **先查后写。** 实现前检查 `frontend/package.json`、`package-lock.json`、`frontend/src/components/`、`frontend/src/assets/style.css`。先确认项目已有依赖、共享组件、图标和样式 token 能否满足需求。
2. **已有能力必须复用。** 若已有依赖或组件可以正确满足功能、交互、可访问性和性能要求，直接复用，不得再手写一套同职责的组件或行为。弹窗、菜单、下拉选择、日期选择、提示消息、进度、图表等通用能力都要先查现有实现。
3. **新增依赖有门槛。** 只有现有依赖和共享组件无法满足明确需求时，才可新增依赖。先检查是否有重复职责的库，并在改动说明中写明现有方案缺少什么。优先选择源码可审阅、维护活跃、版本可通过锁文件固定的成熟库；禁止同一职责无理由引入多个库，也禁止依赖运行时 CDN 注入代码。
4. **自实现是最后手段。** 只有没有合适的成熟依赖或共享组件，或它们无法满足明确的功能、无障碍、兼容性、性能要求时，才自实现。自实现后应封装为可复用组件，不在多个页面复制粘贴同一行为。

## 统一设计语言

- 全站沿用 `frontend/src/assets/style.css` 的颜色、排版、间距、圆角、边框、阴影和语义状态 token。新增视觉值先考虑扩展公共 token，避免每个页面各自定义颜色或尺寸。
- 优先复用现有基础样式（如 `.page`、`.page-head`、`.card`、`.form-row`、`.btn`）、`AppIcon` 与共享组件。相同语义的状态、按钮、输入控件和空状态在不同页面保持一致。
- 新组件先确定是否具有跨页面价值；若会复用，将其放入 `frontend/src/components/`，并共用项目 token。禁止只为当前页面复制一份已有组件并稍作改色。
- 使用图标传递信息时，图标必须语义明确；仅图标按钮仍须有可访问名称。不要为了填满空间添加无意义装饰或多套图标风格。

## 可见文案与信息密度

### 默认原则

界面不主动解释用户已经能从结构和控件看懂的信息。先用布局传递关系，再决定是否真的需要文字。可见文案越少越好，但不能让操作、选项、状态或错误变得含糊。

### 必须避免

- 每个页面标题下面都加一段重复标题含义的副说明。
- 每张卡片都附一行解释，即使标题、数据和按钮已经说明用途。
- 在字段标签、占位符、按钮旁重复同一要求。
- 给显而易见的操作添加教程式提示、欢迎语、营销句或装饰性文案。
- 把“暂无数据”的原因、下一步和鼓励话写成多句段落；空状态默认一行，只有必要时提供一个直接动作。
- 为每个分区机械地添加“说明”“提示”“温馨提示”等辅助标签。

### 允许添加文字的条件

仅在文字对完成操作或避免错误确有帮助时出现，例如：

- 用户无法从字段名或控件本身判断应输入什么，且占位符不足以表达。
- 有重要格式、范围或前置条件，不说明就容易提交失败或造成错误数据。
- 状态、评分、审核结果或下一步不能通过布局、图标和标准状态色清楚表达。
- 错误需要告诉用户如何恢复，或高风险操作需要明确后果。

说明必须放在相关控件或状态旁，使用最短的直接表达；问题解决后不再保留。不要重复标题、字段、按钮或已有状态文本。

### 精简文案的边界

- 输入控件仍需要清晰、可见的字段标签；占位符不能替代标签。
- 图标、颜色或位置不能单独承载关键状态或错误含义，必要时配一个短文本。
- 保留 `label`、`aria-label`、`aria-describedby` 等无障碍语义。无障碍名称可以不显示在页面上，不因此增加视觉辅助文案。
- 短文案必须具体，例如“上传失败，请重试”，不要用“遇到了一点小问题，别担心……”一类长句掩盖错误。

## 提交前的界面检查

逐项检查：

1. 是否先复用了已有依赖、组件、图标或 token？新增库是否真的不可避免，是否引入了重复职责？
2. 是否出现重复标题说明、卡片解释句、冗余提示或可删掉的装饰文字？删掉后，用户是否仍能完成操作并理解状态？
3. 新增颜色、间距、阴影或交互是否遵循现有设计语言？重复出现的行为是否已抽成共享组件？
4. 删除可见辅助文案后，字段标签、键盘操作和无障碍名称是否依旧完整？
